# 设备接入识别与阻断控制系统 — 总体框架设计与任务需求

> 面向家庭或小型办公网络的设备接入识别与阻断控制系统
> 技术栈:Python (Scapy + FastAPI) + React (Ant Design) + SQLite

---

## 一、项目概述

### 1.1 项目背景

随着物联网与移动设备的普及,家庭和小型办公网络中接入的设备越来越多。未经授权的设备(如蹭网设备、可疑终端)可能带来数据泄漏、内网渗透、带宽占用等安全风险。本项目设计并实现一个轻量级的"设备接入识别与阻断控制系统",通过主动扫描 + 被动监听的方式发现局域网内所有在线设备,建立设备画像,识别异常接入行为,并提供阻断与审计能力。

### 1.2 系统目标

系统需要达成以下五个核心目标:第一,自动发现局域网内所有在线设备并维护设备资产清单;第二,基于 IP/MAC/主机名/厂商 OUI 等信息建立设备身份画像;第三,通过白名单、黑名单与规则引擎识别异常接入;第四,对异常或黑名单设备执行逻辑阻断(ARP 欺骗 / iptables / 路由器联动);第五,提供可视化界面和完整审计日志,满足追溯需求。

### 1.3 适用场景

家庭无线网络的访客管理与防蹭网;小型办公网络的资产盘点与访问控制;实验室、教学场景的网络安全演示。

## 二、总体框架设计

### 2.1 系统分层架构

系统采用经典的四层架构:**采集层 → 数据层 → 业务逻辑层 → 表示层**。

| 层次 | 主要职责 | 关键技术 |
|------|----------|----------|
| 表示层 (Presentation) | 可视化展示、用户交互、报表导出 | React 18 + Ant Design 5 + ECharts |
| 业务逻辑层 (Service) | 设备识别、风险判定、策略执行、审计 | FastAPI + APScheduler + Pydantic |
| 数据层 (Data) | 设备资产、日志、规则、配置的持久化 | SQLite + SQLAlchemy ORM |
| 采集层 (Collector) | 网络扫描、流量监听、ARP/DHCP 嗅探 | Scapy + python-nmap + psutil |

### 2.2 核心模块划分

系统划分为 8 个核心模块,各自承担明确职责且通过定义良好的接口协作。

**(1) 设备发现模块 (Discovery)**:负责主动扫描局域网,采用 ARP 扫描 + ICMP Ping + Nmap 端口探测组合手段。支持周期性扫描(默认 30s)和按需触发扫描。

**(2) 设备指纹模块 (Fingerprint)**:基于 MAC OUI 数据库识别厂商,通过 DHCP Option 55、TTL、TCP 窗口大小等被动指纹识别操作系统,通过 mDNS/NetBIOS/UPnP 获取主机名。

**(3) 设备登记模块 (Registry)**:维护设备资产表,支持白名单、黑名单、未知三类分类。新发现设备默认进入未知列表等待人工审核。

**(4) 数据采集模块 (Telemetry)**:记录每台设备的 IP、MAC、主机名、首次上线、最后在线、累计在线时长、流量摘要、访问目标 IP/域名 摘要。

**(5) 风险判定模块 (Risk Engine)**:基于可配置的规则集判定风险等级(低/中/高/严重)。规则示例包括:陌生 MAC 出现在非工作时间、设备 MAC 变化频繁、扫描行为(端口扫描特征)、与黑名单 IP 通信等。

**(6) 阻断控制模块 (Blocker)**:支持三种阻断策略 —— ARP 欺骗(向目标设备发送伪造网关 ARP,使其无法访问外网)、iptables/nftables 规则(适用于网关部署)、路由器 API 联动(适用于支持 OpenWRT/AC 控制器的环境)。

**(7) 审计日志模块 (Audit)**:记录所有接入事件、告警事件、放行操作、阻断操作,字段包括时间戳、设备标识、操作类型、操作人、原因。

**(8) 可视化模块 (Dashboard)**:提供设备列表、风险概览、实时告警、审计回放、规则配置等界面。

### 2.3 数据流设计

系统运行时的核心数据流如下:

1. **扫描线程**周期性调用 Discovery 扫描局域网,得到 (IP, MAC) 对列表;
2. 列表交由 **Fingerprint** 补全厂商、OS、主机名等画像信息;
3. **Registry** 比对资产表,标记设备状态为「在线/离线/新发现」;
4. **Telemetry** 更新设备在线时间、流量统计等动态字段,并写入历史表;
5. **Risk Engine** 对每台在线设备运行规则,生成风险等级,触发时写入告警表;
6. 命中"自动阻断"规则的设备进入 **Blocker** 队列执行阻断动作;
7. 所有动作经 **Audit** 模块统一落盘;
8. **Dashboard** 通过 REST API 和 WebSocket 拉取/推送数据展示给用户。

### 2.4 部署架构

推荐部署方式为单机一体化部署:一台接入局域网的 Linux 主机(树莓派、迷你 PC、或网关本身)运行后端服务,后端同时作为静态资源服务器托管 React 构建产物。需要执行 ARP 扫描和阻断时,服务以 root 或具备 `CAP_NET_RAW` / `CAP_NET_ADMIN` 能力的用户运行。

## 五、核心数据模型

### 5.1 device 表(设备资产)

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| mac | TEXT UNIQUE | MAC 地址(主标识) |
| ip | TEXT | 当前 IP |
| hostname | TEXT | 主机名 |
| vendor | TEXT | OUI 厂商 |
| os_guess | TEXT | 操作系统猜测 |
| category | TEXT | white / black / unknown |
| risk_level | INTEGER | 0=低 1=中 2=高 3=严重 |
| status | TEXT | online / offline / blocked |
| first_seen | DATETIME | 首次发现 |
| last_seen | DATETIME | 最近在线 |
| note | TEXT | 备注 |

### 5.2 access_log 表(接入历史)

记录每次上线/下线/IP 变化事件,字段包括 id、device_id、event_type (`online`/`offline`/`ip_change`)、ip、timestamp。

### 5.3 alert 表(告警)

记录风险引擎产生的告警,字段包括 id、device_id、rule_id、level、message、status (`open`/`acknowledged`/`closed`)、created_at。

### 5.4 rule 表(规则)

记录风险判定规则,字段包括 id、name、condition_json(规则 DSL)、action (`alert`/`block`)、level、enabled。

### 5.5 audit_log 表(审计)

记录所有人工/自动操作,字段包括 id、actor (`system` / 用户名)、action、target_device_id、reason、timestamp。

## 六、API 设计概览

后端对外暴露 RESTful API,统一前缀 `/api/v1`,主要路由分组如下:

设备相关 — `GET /devices`(分页列表+筛选)、`GET /devices/{id}`、`PATCH /devices/{id}`(改备注/分类)、`POST /devices/{id}/whitelist`、`POST /devices/{id}/blacklist`。

扫描相关 — `POST /scan/trigger`(手动触发一次扫描)、`GET /scan/status`(当前扫描进度)。

告警相关 — `GET /alerts`、`POST /alerts/{id}/ack`(确认告警)。

规则相关 — `GET /rules`、`POST /rules`、`PUT /rules/{id}`、`DELETE /rules/{id}`。

阻断相关 — `POST /blocker/{device_id}/block`、`POST /blocker/{device_id}/unblock`、`GET /blocker/active`(当前生效的阻断列表)。

审计相关 — `GET /audit`(分页+时间范围筛选)、`GET /audit/export`(CSV 导出)。

WebSocket — `WS /ws/realtime` 推送设备上下线、新告警、阻断动作等实时事件。

## 七、任务需求与工作分解 (WBS)

将整个项目划分为 5 个阶段、共约 28 个子任务,建议总工期 4~6 周(单人)或 2~3 周(2~3 人小组)。

### 阶段一:环境与脚手架(3 个任务,预计 2 天)

1. **T1.1 项目初始化**:创建仓库、目录结构、`.gitignore`、`.env.example`、README。
2. **T1.2 后端脚手架**:`pyproject.toml`、依赖安装、FastAPI 最小可运行 `main.py`、健康检查路由。
3. **T1.3 前端脚手架**:Vite 创建 React + TS 项目、引入 Ant Design、配置 axios、跑通登录页或空白布局。

### 阶段二:核心功能开发(12 个任务,预计 10~15 天)

4. **T2.1 数据库与 ORM**:实现 5 张表的 SQLAlchemy 模型 + `init_db.py`。
5. **T2.2 网卡与网段识别**:`utils/net.py` 自动识别本机 LAN 网段。
6. **T2.3 ARP 扫描**:Scapy 实现 `discovery.py` 的 ARP 扫描函数,返回 (IP, MAC) 列表。
7. **T2.4 ICMP/Nmap 探测**:补充活性探测,获取更准确的在线集合。
8. **T2.5 OUI 厂商识别**:`fingerprint.py` 集成 manuf 库,根据 MAC 前缀解析厂商。
9. **T2.6 主机名采集**:通过 mDNS / NetBIOS / DHCP 抓取主机名。
10. **T2.7 设备注册与分类**:`registry.py` 实现白/黑/未知三态切换。
11. **T2.8 状态采集与持久化**:周期性更新 `device` 表的 `last_seen`、生成 `access_log`。
12. **T2.9 风险规则引擎**:`risk_engine.py` 读取 `rule` 表执行判定,内置 5 条默认规则。
13. **T2.10 ARP 阻断实现**:`blocker.py` 实现 ARP 欺骗阻断与撤销。
14. **T2.11 iptables 阻断实现**(可选):提供网关部署模式下的 nftables 规则下发。
15. **T2.12 审计日志**:`audit.py` 统一封装审计写入,所有写操作必须经此模块。

### 阶段三:接口与前端(8 个任务,预计 7~10 天)

16. **T3.1 设备相关 API**:实现 6 个设备路由,含分页、筛选、排序。
17. **T3.2 告警 / 规则 / 阻断 / 审计 API**:实现剩余 REST 接口。
18. **T3.3 WebSocket 推送**:实现连接管理与事件广播。
19. **T3.4 前端布局与路由**:左侧菜单 + 顶栏 + 6 个页面的路由骨架。
20. **T3.5 仪表盘页**:总设备数、在线数、风险分布饼图、最新告警列表。
21. **T3.6 设备管理页**:表格 + 详情抽屉 + 白/黑名单切换按钮。
22. **T3.7 告警 & 审计页**:列表 + 筛选 + 详情。
23. **T3.8 规则配置页**:可视化编辑 condition_json 的简易表单。

### 阶段四:测试与加固(3 个任务,预计 3~4 天)

24. **T4.1 单元测试**:对 discovery / fingerprint / risk_engine / blocker 编写 pytest 用例。
25. **T4.2 集成测试**:模拟设备上下线,验证端到端流程与 WebSocket 推送。
26. **T4.3 安全加固**:API 鉴权(JWT 或简单 Token)、输入校验、阻断操作二次确认、最小权限运行。

## 八、风险点与注意事项

实现过程中需要重点关注以下风险:

**权限与合规** — ARP 扫描和阻断需要 root / `CAP_NET_RAW` / `CAP_NET_ADMIN`,部署时务必使用专用账号并最小化授权;在他人网络中使用本系统须取得授权,避免触及法律红线。

**ARP 阻断的副作用** — ARP 欺骗会持续向目标设备广播伪造响应,可能误伤同网段其他设备,且在严格的交换机(DAI 防护)下失效。建议在生产部署时优先使用网关 iptables 方案。

**MAC 伪造规避** — 攻击者可能伪造白名单设备 MAC,系统应记录 MAC 突然出现在异常时段、与已知设备指纹不一致等可疑模式。

**扫描频率与噪声** — ARP 扫描过于频繁会产生网络噪声并被 IDS 告警,默认 30s 一次较为合理,可在配置中调整。

**前后端时钟一致性** — 所有时间戳使用 UTC 存储,展示时按浏览器时区转换。

## 九、验收标准

系统通过验收需要同时满足以下条件:能够在 1 分钟内发现新接入设备并写入数据库;白名单设备永不触发自动阻断;黑名单设备接入后 5 秒内被阻断并产生审计记录;界面上的设备列表、告警、审计可正常展示并支持筛选;所有写操作都能在审计日志中找到对应记录;单元测试覆盖率不低于 60%;具备完整的部署手册和演示材料。
